## Kernel read (money math)
- **openingSale.ts** uses the same broken test, closed form, tax, loan and basis updates as the kernel's step-5 margin branch: S = (L − t·V)/(1 − g·tax − t), broken when S ≥ V or !(S > 0). The one difference is the extra up-front `L > 0 && (V <= 0 || L >= V)`. Its `L > 0` guard keeps balance 0 (including portfolio 0) on the old month-0 path. A scratch replica of the in-loop branch matches it exactly (`===`) on 468 states. A path that starts at L=50 and borrows into L=70 lands, after its in-loop call, on the same net worth as the opening sale at L=70 (difference 0), but counted as a call ([opening-sale-probe.txt](opening-sale-probe.txt)).
- **Clamps:** `kernelOpeningSale` takes `cfg.portfolio`, `cfg.portfolio·cfg.basisFraction` (clamped to [0, 1]), `cfg.targetLtv` (min(target, maxLtv)), `cfg.maxLtv` and `cfg.tax`, the same values the loop reads. `existingLoanInfo` in the UI applies the same clamps. Over 135 cases (basis −0.2…1.3, target 0.3…0.7, balance 0…$2,999,999) its status and sale amounts equal simulate's, with 0 mismatches.
- **Start state:** the opening sale is computed once per run and is the same on every path. `called` is set only when the path is broken from the start, so the sale never bruises a path or feeds marginCallByYear. Year 0 records the post-sale V, L, V − L, L/V; a path broken from the start records 0/0/0/1.
- **Sell side:** stays `max(0, V0 − L0)` with basis `B0·Vs0/V0`, from today's V before any sale.
- **Edge behaviour, not a defect:** with `targetLtvAfterCall` ≥ `maxLtv`, the target is clamped to the line. The sale then lands exactly on the line, and the first month's interest triggers a real month-0 margin call (outcome 1). The defaults (0.45 under 0.6) don't hit this.
